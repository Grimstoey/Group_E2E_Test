## CI เป็นแค่ "คนกดปุ่ม"

<div class="cols">
<div>

**Logic อยู่ใน repo — ไม่ใช่ใน CI**

```bash
npm run typecheck
npm run test:unit        # หรือ test:coverage
npm run test:integration
npm run test:e2e
```

คำสั่งเดียวกับที่รันในเครื่อง
ผ่านในเครื่อง ⇔ ผ่านใน CI

</div>
<div>

**CI เพิ่มแค่ 3 อย่าง**

1. รัน **ทุก push / merge request** — ไม่มีใครลืม
2. เครื่อง **สะอาด** ทุกครั้ง — ไม่มี "ในเครื่องผมมี table นี้"
3. **คนทั้งทีมเห็น** ว่าแดงหรือเขียว

</div>
</div>

> ถ้า pipeline มี shell script 40 บรรทัดที่ไม่มีในเครื่อง → debug ได้แค่ใน CI → ช้าและเจ็บ

## ไฟล์ pipeline 3 แบบ ทำงานเหมือนกัน

| CI | ไฟล์ | Docker มาจากไหน | Postgres อยู่ที่ |
|---|---|---|---|
| **GitHub Actions** | `.github/workflows/ci.yml` | Docker บน runner `ubuntu-latest` | `localhost:5433` |
| **GitLab CI** | `.gitlab-ci.yml` | service `docker:29-dind` (runner ต้อง `privileged = true`) | **`docker:5433`** |
| **Jenkins** | `Jenkinsfile` | Docker ของ agent label `docker` | `localhost:5433` |

## GitHub Actions

<div class="cols">
<div>

```yaml
jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run typecheck
      - run: npm run test:coverage
```

</div>
<div>

```yaml
  integration:
    needs: unit          # ← fail fast
    steps:
      - ...
      - run: npm run db:test-rollback
      - run: npm run test:integration

  e2e:
    needs: integration
    steps:
      - ...
      - run: npm run test:e2e
      - if: failure()
        run: docker compose --profile e2e logs app
```

</div>
</div>

Docker มีอยู่แล้วบน runner — `docker compose` ใน npm script ใช้ได้ทันที

## GitLab CI & Jenkins: จุดที่ต่าง

<div class="cols">
<div>

**GitLab — docker-in-docker**

```yaml
.with-docker:
  services:
    - name: docker:29-dind
      alias: docker
  variables:
    DOCKER_HOST: tcp://docker:2375

integration:
  extends: .with-docker
  variables:
    DATABASE_URL: postgres://…@docker:5433/election_test
```

container รันอยู่ **ใน service `docker`** → port ที่ publish อยู่ที่ host `docker` ไม่ใช่ `localhost`

</div>
<div>

**Jenkins — agent ใช้ซ้ำ**

```groovy
options {
  disableConcurrentBuilds()
}
post {
  always {
    dir('app') {
      sh '''docker compose --profile e2e \
            --profile tools down -v \
            --remove-orphans || true'''
    }
  }
}
```

agent **ไม่ถูกทิ้ง** หลัง build → ต้องเก็บกวาดเอง และห้าม 2 build ชน port เดียวกัน

</div>
</div>

## Quality gate 1: coverage — เฉพาะที่ควรครอบคลุม

```js
// jest.config.js
collectCoverageFrom: ['src/**/*.ts', '!src/server.ts'],
coverageThreshold: {
  './src/domain/':   { statements: 100, branches: 100, functions: 100, lines: 100 },
  './src/services/': { statements: 75,  branches: 70,  functions: 90,  lines: 80 },
},
```

- **ทำไมไม่ตั้งทั้ง project?** `routes/` และ `repositories/` ถูกทดสอบโดย *integration* ไม่ใช่ unit
  → ตั้ง threshold รวม = บังคับให้เขียน unit test ที่ mock SQL (ผิด boundary)
- coverage บอกว่า **บรรทัดไหนไม่เคยถูกรัน** — ไม่ได้บอกว่าบรรทัดที่รันถูก **ตรวจ**
  `it('hash', () => { hashPassword('x') })` ได้ coverage แต่ไม่มี assertion

## Quality gate 2: migration ถอยกลับได้จริง

```bash
npm run db:test-rollback
# = liquibase update-testing-rollback
#   update → rollback ทุก changeset → update อีกรอบ
```

```sql
--changeset election:005-add-district-closed-at
ALTER TABLE districts ADD COLUMN closed_at TIMESTAMPTZ;
--rollback ALTER TABLE district DROP COLUMN closed_at;      -- ← พิมพ์ผิด: district
```

- ไม่มี gate → รู้ตอน production ต้อง rollback **ตอนตี 2**
- มี gate → CI แดงตั้งแต่ merge request

## e2e ช้า — รันทุก push ไหม?

| ทางเลือก | เมื่อไหร่เหมาะ |
|---|---|
| ทุก push (ที่เราทำ) | suite เล็ก (< 5 นาที) |
| เฉพาะ merge request + `main` | suite กลาง, ทีมหลายคน |
| nightly | suite ใหญ่ — แต่ bug จะถูกเจอช้าขึ้น 1 วัน |
| **shard** ขนานหลายเครื่อง (`playwright test --shard=1/4`) | suite ใหญ่ที่ต้องรู้ผลเร็ว |

ถ้า e2e ใช้ 15 นาที — ปัญหาอาจไม่ใช่ CI แต่คือ **มี e2e มากเกินไป** (กลับไปดู Lab 01)
